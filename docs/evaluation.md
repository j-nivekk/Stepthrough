# How well Stepthrough finds steps

This page reports how Stepthrough's step detection was tested, how well it does, and where it goes wrong. It
covers the engine that every new run uses, **stable screens** (`stable_v3`, engine version 1.1.0).
[Section 5 of the guide](../GUIDE.md#5-how-stepthrough-finds-steps) explains how it works in plain terms, and
[`backend/README.md`](../backend/README.md) lists its settings.

Every test recording is generated by code, so the exact time of every change is known, and anyone can
regenerate the recordings and repeat the numbers. No real recordings are used.

All numbers below were measured on 8 November 2026, with the engine as of commit `865003f`, on a Mac (Apple M4)
with FFmpeg 9.0.2, OpenCV 4.10 and Python 3.12. [Section 5](#5-reproducing-these-numbers) shows how to repeat
them.

Those measurements were made with engine version 1.0.0. Version 1.1.0 changes labels only: a pop-up is now
recognised whatever dark colour dims the screen under it and when dark areas such as a header bar sit beside
it, and a pop-up that closes gets its own label (*modal closed*). The interface scenarios in section 3 were
measured again with 1.1.0 on 12 November 2026 and give the same table. The other numbers were not measured
again.

## Summary

- **Interface scenarios.** On 25 generated recordings of made-up apps (49 changes), encoded the way uploads
  arrive, Stepthrough found 48 or 49 of the 49 changes (F1 0.97 to 0.98). Every matched screenshot showed the
  screen after it had settled.
- **Phones.** At the sizes phones record at (iPhone, Android phone), and in every upload format tested (H.264,
  HEVC, WebM, rotated, full range, HDR PQ and HLG, 30 and 60 fps), every change was found with the right
  screenshot. The only extra step was a dialog closing, which is a real screen.
- **Computers and tablets are weaker.** Typing into a field is split into several steps, and on a computer
  the step can show unfinished text. On a computer, scrolling through a list whose rows look alike can be
  missed. Lowering the smallest change fixes both (see [section 4](#4-limits-and-edge-cases)).
- **A moving mouse pointer** lowers F1 to 0.84 on the small test recordings.
- **Labels** (navigation, scroll, and so on) match the kind of change about 60 to 70 % of the time, and far
  less on a desktop screen. Treat them as hints, not as data.
- **Test cards** confirm the timing (a countdown is found to the second, also with a dial that keeps turning),
  show that a change to another colour of the same brightness is not seen, and measure the colours of the
  working copy: within 1 level of the original for ordinary uploads, but up to 14 levels off for saturated
  colours in HDR recordings.

## 1. What is being tested

A step is a screen that stays still for at least the **minimum time on screen**. For each such screen,
Stepthrough keeps one screenshot, taken 200 ms after the screen settles. In short:

1. Every upload is first turned into a *working copy*: a steady frame rate (at most 30 frames per second), the
   right way up, and standard colours (HDR recordings are converted).
2. The working copy is analysed at 15 frames per second, in grey, at 480 pixels on the long side.
3. Stepthrough measures how much the picture flickers from compression, and only counts a pixel as changed when
   it changes by several times that amount, and by at least 10 grey levels out of 255.
4. A screen ends when a connected area larger than the **smallest change** differs from the first frame of that
   screen. The area is counted in blocks of 8 × 8 pixels of the analysis frame. Areas that keep moving (a
   spinner, a blinking cursor), the phone's status bar and areas the user marks are ignored.
5. Afterwards, bursts of typing are grouped into one step, each step gets a label, and returns to an earlier
   screen are marked as revisits.

The defaults depend on the recording type:

| recording type | minimum time on screen | smallest change |
| --- | --- | --- |
| phone or tablet | 450 ms | 0.10 % of the screen |
| computer | 600 ms | 0.25 % of the screen |

## 2. How it was tested

All test recordings are drawn by the code in [`backend/tests/eval`](../backend/tests/eval), together with a
list of when each change happens. Each one goes through the app's own pipeline (working copy, then detection)
with the default settings for its recording type.

### Interface scenarios

25 short recordings of made-up interfaces at 640 × 360 pixels, with 49 changes in total:

- **navigation:** plain cuts, fades, a dark theme, and screens that change quickly one after another;
- **scrolling:** a list, a very slow scroll, and a scroll followed by navigation;
- **feeds:** card swaps, a scrolling feed, full-screen swipes (fast and slow), and a feed with a fixed overlay;
- **overlays:** a dialog, a toast notification and a bottom sheet;
- **content:** changed numbers, a loading screen filling in, typing, and a long still screen;
- **sessions:** a longer browsing session, going back and forth between two screens, and a noisy recording;
- **what a step should be:** a chat message typed word by word with pauses (one step), two form fields filled
  in turn (one step each), and three switches toggled in a column (three steps, not one typing burst).

Each recording is encoded the way uploads arrive, with four kinds of on-screen noise added:

| variant | what it simulates |
| --- | --- |
| `raw` | the generated file itself, nearly lossless |
| `h264_cfr` | a compressed upload with a steady frame rate (H.264) |
| `h264_vfr` | a phone screen recording: a frame is only written when the screen changes (at least one per second) |
| `+cursor` | a blinking text cursor |
| `+spinner` | a loading spinner that keeps turning |
| `+pointer` | a mouse pointer that keeps moving (analysed with the **computer** recording type) |
| `+clock` | a status-bar clock that ticks every second |

### Device sizes

Six of the scenarios (a fade between three screens, a list scroll, a bottom sheet, a dialog, typing into a
form, and a browsing session with a scroll, a dialog and two screen changes) are drawn again at the sizes devices
record at, as phone-style uploads:

| device | recorded size | recording type |
| --- | --- | --- |
| iPhone | 1180 × 2556 (H.264 and HEVC) | phone |
| Android phone | 1080 × 2400 | phone |
| tablet | 1640 × 2360 | phone |
| Retina laptop | 2560 × 1600, with and without a moving pointer | computer |
| desktop | 1920 × 1080, with and without a moving pointer | computer |
| full-screen video, upright and sideways | 1080 × 1920 and 1920 × 1080 (a feed swipe only) | phone |

The computers use five of the six scenarios (no bottom sheet).

### Upload formats

The six phone scenarios, at 780 × 1688, in every format the app is likely to meet: H.264 with a steady and with
a variable frame rate, HEVC (as iPhones record), WebM (VP9), a file stored sideways with rotation information,
H.264 tagged as BT.709, full-range H.264, 10-bit HDR in PQ and in HLG, and phone-style uploads recorded at
60 and 120 frames per second.

### Test cards

Generated screens that each check one thing exactly:

- **countdown:** colour bars and a grey ramp that never change, and a large digit that changes every second
  (8 changes). A second version adds a dial whose hand turns once a second, like a countdown leader or a
  progress ring. Run at three sizes: a small phone, an iPhone and a laptop.
- **same brightness:** the whole screen changes from blue to a brown of the same brightness, then to a clearly
  darker colour.
- **size sweep:** dark squares of growing size appear one by one on a plain screen, from 0.02 % to 0.80 % of
  the screen, to see where the smallest change really draws the line.
- **colour accuracy:** colour bars, a grey ramp, white and black, encoded in each upload format and turned into
  a working copy. Every patch is compared with the original, in 8-bit levels averaged over red, green and blue.
- **long recording:** 17 screens of 20 seconds each (5 minutes 40 seconds). That is longer than the analysis
  keeps in memory, so it has to read the recording twice.

### Scores

- **precision, recall and F1:** a step counts as found when it falls within 500 ms of a known change. Precision
  is the share of steps that match a change, recall the share of changes that were found, and F1 combines both.
- **right screenshot:** whether the exported screenshot shows the screen *after* the change, rather than the
  one before it or a frame half-way through an animation. This is judged in the part of the screen that
  changed, so that a small change such as a switch is not lost in compression noise.
- **opening screen:** whether step 0 is there and shows the first frame. The known changes do not include the
  opening screen, so it is left out of precision and recall.
- **labels:** how often a step's label describes the kind of change it matched.

## 3. Results

### Interface scenarios

| variant | precision | recall | F1 | right screenshot | opening screen | labels |
| --- | --- | --- | --- | --- | --- | --- |
| `raw` | 0.96 | 0.98 | 0.97 | 48/48 | 25/25 | 62 % |
| `h264_cfr` | 0.96 | 1.00 | 0.98 | 49/49 | 25/25 | 63 % |
| `h264_vfr` | 0.96 | 1.00 | 0.98 | 49/49 | 25/25 | 63 % |
| `h264_vfr+cursor` | 0.96 | 1.00 | 0.98 | 49/49 | 25/25 | 63 % |
| `h264_vfr+spinner` | 0.96 | 0.98 | 0.97 | 48/48 | 25/25 | 62 % |
| `h264_vfr+pointer` | 0.82 | 0.86 | 0.84 | 40/42 | 25/25 | 64 % |
| `h264_vfr+clock` | 0.96 | 1.00 | 0.98 | 49/49 | 25/25 | 63 % |

Detection takes 5 to 6 seconds for all 25 recordings together.

- **Extra steps (precision 0.96).** Two steps are added when the screen goes back to how it was before: a
  toast that disappears, and a dialog that is closed. These are real screens, but the list of changes does not
  include them.
- **A moving mouse pointer.** A typed chat message and two form fields are split into extra steps, two
  screenshots show the wrong state, and seven changes are missed. Four of the misses are in the "rapid"
  recordings, whose screens last 0.5 to 0.6 seconds: shorter than the computer type's 600 ms minimum. Two are
  list scrolls, missed for the reason described under *Computers and tablets* in section 4.
- **Two misses that are not explained yet.** The plain list scroll is missed in the nearly lossless `raw` file
  but found in every compressed version. The very slow scroll (under one pixel per frame) is missed when a
  spinner is added. Both look like cases that sit right at a threshold.

- **Phones.** Every change is found with the right screenshot. The one extra step on every device is the
  dialog closing in the browsing session.
- **Tablet.** Typing into the form is split into three steps instead of one.
- **Computers.** Typing is not grouped. On the laptop it becomes two steps, and on both computers the matched
  step shows the text before it was finished. In the browsing session on the laptop, the scroll through the
  list is missed. Both come from the computer's smallest change (0.25 %): each typed character, and each
  difference between list rows that share a layout, is far smaller than that. With the smallest change at
  0.10 % the scroll is found, and at 0.05 % the typing becomes one step showing the finished text.
- **Labels on the desktop** are almost all wrong (11 %), and full-screen video swipes are not labelled
  *feed swap*.
- The moving pointer made no difference on these computer recordings.

screen that the encoder sharpens when it writes its next frame a second later counts as a change, which adds

### Test cards

- **Countdown.** All 8 digit changes were found at the right second, with the right screenshot and no extra
  steps, at all three sizes, with and without the turning dial.
- **Same brightness.** The change from blue to brown was not seen on the phone or the laptop. The change to the
  darker colour was.
- **Size sweep.** The line falls well below the setting, because a square that straddles a block border counts
  as several whole 8 × 8 blocks:

  | screen | smallest change setting | not found | found |
  | --- | --- | --- | --- |
  | phone 390 × 844 and iPhone 1180 × 2556 | 0.10 % | 0.02 % | 0.04 % and larger |
  | laptop 1280 × 800 (computer) | 0.25 % | 0.15 % and smaller | 0.20 % and larger |

- **Colour accuracy** of the working copy (1280 × 720, all patches):

  | upload | average difference | largest difference |
  | --- | --- | --- |
  | H.264, untagged | 0.2 | 1.0 (grey 230) |
  | H.264 tagged BT.709 | 0.1 | 1.0 (grey 230) |
  | H.264, full range | 0.2 | 1.0 (grey 230) |
  | HEVC | 0.2 | 1.0 (grey 230) |
  | WebM (VP9) | 1.4 | 2.7 (white) |
  | stored sideways, with rotation | 1.4 | 2.7 (white) |
  | HDR PQ | 5.8 | 14.3 (75 % green) |
  | HDR HLG | 1.9 | 10.9 (75 % green) |

  Ordinary uploads keep their colours to within about one level. HDR recordings are converted to standard
  colours with a 33-point colour table. White comes out at 247 (PQ) and 250 (HLG), where the conversion aims
  for about 250, so that brighter HDR highlights still fit. Saturated colours lose some saturation: the 75 %
  green bar keeps its green but gains up to 26 levels of red and blue.
- **Long recording.** All 16 changes in the 5 minute 40 second recording were found, each screenshot showed the
  right colour, there were no extra steps, and the whole test (making the recording, the working copy and the
  detection) took 8 seconds.

## 4. Limits and edge cases

### What it does not see

- **Changes in colour only.** Frames are compared in grey, so a change between two colours of the same
  brightness is not seen (see the test card above).
- **Changes below the smallest change.** The line is fuzzier than the setting suggests, because the area is
  counted in 8 × 8 blocks: changes several times smaller than the setting can count (section 3). Changes that
  are smaller still, such as a single typed character on a computer screen, are ignored.
- **Screens shorter than the minimum time on screen** are skipped, by design. This is behind the misses in the
  "rapid" recordings.
- **Something that never stops moving.** A playing video or a large animation keeps the screen from being
  still, so it hides the steps around it. Stepthrough only ignores moving areas by itself when they are small
  (under a quarter of the screen) and keep changing second after second, like a spinner or the turning dial on
  the countdown card. Anything slower or larger, such as a carousel that turns every few seconds or a
  full-screen video, needs an ignore area.

### What it sees too much

- **Returns to an earlier screen** (a toast going away, a dialog closing) are steps of their own, marked as
  revisits.
- **Notifications and system overlays** are real changes on screen and become steps. Turning on Do Not Disturb
  before recording avoids them. iPhone recordings started from Control Centre begin with Control Centre on
  screen, which becomes a step to reject.
- **Encoder sharpening at high frame rates.** In phone-style uploads recorded at 120 frames per second, a still
  screen can count as a new step when the encoder sharpens it.
- **Desktop recordings.** The computer type ignores small changes such as a moving pointer, but hover effects
  (tooltips, highlighted buttons) are real changes and can become steps.

### Computers and tablets

- **Typing on a computer** is not grouped, because each character is far below the computer's smallest change
  (0.25 %). The text appears in steps part-way through, and the finished text can be missed. Set the smallest
  change to 0.05 % for recordings with typing, and keep the mouse still while typing.
- **Scrolling through a uniform list on a computer** can be missed: after the scroll, every difference is a
  word-sized patch below 0.25 %, so the scrolled list counts as the same screen. A smallest change of 0.10 %
  finds it.
- **Typing on a tablet** is split into several steps.
- These were found in generated recordings at 1280 × 800 and larger; real desktop interfaces with smaller text
  are likely to be affected more.

### Labels and revisits

- Labels describe the change and never decide what counts as a step. They agree with the kind of change about
  60 to 70 % of the time, and 11 % on the 1080p desktop. Known mix-ups: full-screen video swipes are not
  labelled *feed swap*, panels that slide in without dimming the screen are labelled *update*, and a swap of
  feed cards can only be told apart from a long scroll when the swipe covers about one full screen.
- A revisit means "the same picture by the same test that ends a screen", not "the same page". Two different
  pages that look alike can be linked as revisits, and the same page at a different scroll position is not.

### Recordings and formats

- **Formats.** H.264, HEVC, WebM, rotated files, full-range video and 10-bit HDR (PQ and HLG) all give the same
  steps. Phone-style recordings are resampled by real time, so every analysed frame has its true time;
  recordings above 30 frames per second are resampled to 30.
- **HDR colours.** HDR recordings are converted to standard colours with a 33-point colour table, which loses
  some saturation: on the test card, the 75 % green bar is off by 14 levels on average for PQ and 11 for HLG,
  mostly as added red and blue. White lands at 247 (PQ) and 250 (HLG). The steps are not affected; a finer
  table would improve the screenshots.
- **Files whose stated length is too short.** The working copy ends at the duration the file states. FFmpeg's
  MP4 muxer can state a duration that ends before the last frame, for variable-frame-rate video with B-frames
  that ends on a still screen; such a file loses its last screen. Recordings made by phones and by macOS are
  not affected.
- **Different FFmpeg versions** make the same working copy: the colour conversion is set up so that FFmpeg 7.1
  and 9.0.2 give identical pixels.
- **Long recordings.** The analysis keeps its small grey frames in memory up to 512 MB, about four minutes of a
  computer recording or five of a phone recording. Longer recordings are read a second time instead, with the
  same result (see the long recording above).

### Text recognition

Text recognition (OCR) is not part of finding steps, and its accuracy has not been evaluated beyond a check that
it reads two large words correctly. On Intel and AMD processors it runs without PaddlePaddle's oneDNN
acceleration, which is broken in the version Stepthrough uses, so it is slower there.

### Limits of this evaluation

- **Generated, not real.** The test recordings are drawn by the same project that built the engine, so the
  engine may suit them better than real interfaces. Interfaces are drawn at their logical size and scaled up to
  the device size, so their text is softer than on a real screen. They have no real fonts, animation curves or
  screen-recorder quirks, and nobody hesitates, scrolls with momentum or makes mistakes.
- **Small.** 25 interface scenarios with 49 changes, plus six scenarios at device sizes and in different
  formats.
- **Planned:** a labelled benchmark of real recordings, made with consent across phones, tablets and computers,
  with the settled screens marked by two people independently, so that their agreement can be reported too.
  Scripted walkthroughs of HTML mock-ups in a browser would sit in between: real fonts and animations, with
  the timing still known from the script.

## 5. Reproducing these numbers

From the `backend` folder:

```bash
# interface scenarios, every variant (about two minutes)
uv run python -m tests.eval.stress --set all
# device sizes, upload formats and test cards (about twelve minutes)
uv run python -m tests.eval.wide
# the fast regression checks that run with the normal tests
uv run pytest tests/eval/ -q
```

The test videos are not stored anywhere. They are made again on every run, and deleted afterwards. To keep
them, for watching or for uploading into the app, add `--save-videos` and a folder:

```bash
uv run python -m tests.eval.wide --save-videos tests/eval/results/videos
```

Each video is saved with a `.json` file listing the changes it contains and when they happen. An
`index.csv` file lists every video.

## 6. Background

Detecting steps as stable screens follows the steady-state keyframe method of GIFdroid (Feng and Chen, 2022),
which finds keyframes in GUI recordings as stretches where consecutive frames stay alike for a minimum time.
Earlier versions of Stepthrough instead scored every change with a weighted mix of signals and then looked for
a settled frame after it. That approach was harder to explain and to cite, and it broke down on the variable
frame rate of phone recordings. Those engines are retired: runs made with them still open and export, and
their code is at the git tag `last-with-hybrid-v2`.

- Feng, S. and Chen, C. (2022). GIFdroid: An Automated Light-weight Tool for Replaying Visual Bug Reports.
  *ICSE 2022 Companion*, pp. 95–99. https://arxiv.org/abs/2112.04128
- Feng, S., Xie, M., Xue, Y. and Chen, C. (2023). Read It, Don't Watch It: Captioning Bug Recordings
  Automatically. *ICSE 2023*, pp. 2349–2361. https://arxiv.org/abs/2302.00886
